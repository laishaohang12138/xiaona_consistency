# Benchmark Operator Manual

## Purpose
- This manual explains how to use benchmark mode in daily engineering practice.
- It is written for operators who do not want to read the benchmark code.
- Benchmark is for validation and comparison, not for daily winner selection.

## What Benchmark Is For
Use benchmark when you need to answer one of these questions:
1. Did a rule change make the system better or worse?
2. Did a threshold change create new false passes or false warns?
3. Is one heavy provider more usable than another?
4. Does the shadow view classifier agree with the primary lane router?
5. Is a frozen label set still stable after a code change?

## What Benchmark Is Not For
- It is not the daily batch review workflow.
- It is not a shortcut for final human judgment.
- It is not the same thing as main training admission.
- It should not replace `shot_review -> inspect_review_packet -> promote_winner`.

## Two Benchmark Families

### 1. Replay Benchmark
Replay uses a saved `qa_report.json` plus a human label file.

It is used to validate:
- status accuracy
- lane accuracy
- reason constraints
- shadow view classifier accuracy

Replay does not rerun the main visual feature extraction.

### 2. Heavy Compare Benchmark
Heavy compare uses a saved `qa_report.json`, a label file, and access to source images.

It is used to compare one or more heavy evidence providers, for example:
- `segformer_body_fusion`
- `segformer_parser`
- `body_measure_lite`

Heavy compare does rerun the heavy evidence providers.

## Recommended Use Cases

### Use Replay When
- you changed thresholds
- you changed soft-gate logic
- you changed view-lane policy
- you changed report interpretation rules
- you want fast offline regression checking

### Use Heavy Compare When
- you changed heavy evidence providers
- you want to compare fusion vs single-provider behavior
- you want to measure heavy evidence readiness on a frozen set
- you want to check whether cache hit ratio is healthy

## Do Not Use Benchmark When
- you only need to review today's new batch
- you have not created any human labels yet
- the report file and label file come from different image sets
- the runtime is `engine_fatal`

## Key Input Files

### 1. `qa_report.json`
This is the machine evidence report generated by QA.

Important rule:
- replay benchmark only knows what was written into that report
- if the report is old, new fields will be missing

Example:
- shadow view classifier metrics only work on reports that already contain `view_classifier_shadow`

### 2. Benchmark Label File
This is a human-maintained JSON file with expected outcomes.

Typical fields:
- `expected_status`
- `expected_task_profile`
- `expected_view_lane`
- `expected_view_lane_detail`
- `must_have_reasons`
- `must_not_have_reasons`
- `weight`

### 3. Source Images
Heavy compare needs the original images so it can rerun heavy providers.

If heavy compare cannot resolve the original image path:
- availability drops
- coverage drops
- the compare result becomes weak

## Benchmark Actions

### Action 1. template
Use this to export a label template from an existing `qa_report.json`.

Use it when:
- you are creating a new benchmark label file
- you want the image names and current lane/status fields prefilled

Direct command:

```powershell
.\.venv\Scripts\python.exe .\check_consistency.py `
  --mode benchmark `
  --benchmark-report outputs\qa_report.json `
  --benchmark-template-out outputs\benchmark_labels.interactive.json
```

What to do next:
1. open the exported label file
2. fill the expected fields manually
3. save it as a benchmark label set

### Action 2. replay
Use this to replay a saved report against a label file.

Direct command:

```powershell
.\.venv\Scripts\python.exe .\check_consistency.py `
  --mode benchmark `
  --benchmark-report outputs\qa_report.json `
  --benchmark-labels outputs\benchmark_labels_verify.json `
  --benchmark-output outputs\benchmark_result_verify.json
```

Replay is the default benchmark action.

### Action 3. compare_heavy
Use this to compare heavy evidence providers on the same label set.

Direct command:

```powershell
.\.venv\Scripts\python.exe .\check_consistency.py `
  --mode benchmark `
  --benchmark-report outputs\qa_report.json `
  --benchmark-labels outputs\benchmark_labels_verify.json `
  --benchmark-compare-heavy-providers segformer_body_fusion segformer_parser body_measure_lite `
  --benchmark-image-root input `
  --benchmark-output outputs\benchmark_heavy_compare.json
```

Important:
- `--benchmark-image-root` should point to the directory that contains the original images
- heavy compare requires a usable visual runtime
- if the system is `engine_fatal`, heavy compare should not be used

### Action 4. seal
Use this to update benchmark metadata without hand-editing the JSON top-level fields.

Use it when:
- a label file has become frozen
- you want to record benchmark identity and freeze tag
- you want to prepare the label file for later Optuna use

Example:

```powershell
.\.venv\Scripts\python.exe .\check_consistency.py `
  --mode benchmark `
  --benchmark-seal-labels `
  --benchmark-labels outputs\benchmark_labels_verify.json `
  --benchmark-id front_core_v1 `
  --benchmark-freeze-tag 2026-03-26
```

## How To Build A Good Benchmark Set

### Candidate Review Set
Use this when you are still iterating.

Recommended properties:
- mixed PASS / WARN / FAIL
- includes known edge cases
- does not feed Optuna

### Frozen Benchmark Set
Use this when you want stable regression validation.

Recommended properties:
- human-sealed judgments
- clear benchmark ID
- concrete freeze tag
- stable lane distribution

### Good Coverage Rule
Prefer a benchmark set that covers:
- front mainline
- three-quarter review
- side shadow
- back shadow
- false-pass regressions
- false-warn regressions

## How To Read Replay Output

### Core Metrics
- `exact_accuracy`
  - overall exact status match rate
- `macro_f1`
  - balanced overall classification quality
- `pass_precision`
  - how clean the PASS predictions are
- `false_pass_rate`
  - how often the system wrongly lets bad candidates look safe
- `release_safety_score`
  - the main summary score for release-facing safety

Practical reading rule:
- for this project, `false_pass_rate` matters more than raw accuracy
- a system that is slightly conservative is safer than one that over-passes polluted data

### Agreement Metrics
Replay also reports:
- `task_profile_accuracy`
- `view_lane_accuracy`
- `view_lane_detail_accuracy`
- `reason_constraint_accuracy`

Use these to answer:
- is the profile assignment stable?
- is the lane routing still reliable?
- did a rule change silently alter reason behavior?

### Shadow View Classifier Metrics
Replay now also reports:
- `shadow_view_lane_accuracy`
- `shadow_view_lane_detail_accuracy`
- `shadow_primary_lane_agreement`
- `shadow_view_classifier_metrics.available_weight_ratio`
- `shadow_view_classifier_metrics.confidence_mean`

How to read them:
1. `shadow_view_lane_accuracy`
   - how often the shadow classifier matches the human lane label
2. `shadow_primary_lane_agreement`
   - how often shadow and primary router agree
3. `available_weight_ratio`
   - whether the shadow classifier was actually present in the report

Important:
- if these values are `null` or `0`, check whether the source `qa_report.json` was generated before shadow classifier support existed

## How To Read Heavy Compare Output

### The Main Metrics
For each heavy provider, focus on:
- `available_weight_ratio`
- `confidence_mean`
- `coverage_mean`
- `cache_hit_weight_ratio`
- `cache_write_weight_ratio`
- `cache_miss_weight_ratio`
- `evidence_readiness_score`

### Practical Meaning
- `available_weight_ratio`
  - how often the provider produced usable evidence
- `confidence_mean`
  - average confidence when evidence exists
- `coverage_mean`
  - how much of the expected evidence surface was actually covered
- `cache_hit_weight_ratio`
  - whether repeated runs are reusing cached heavy evidence efficiently
- `evidence_readiness_score`
  - the high-level provider ranking score

Current readiness formula:
- `0.50 * available + 0.25 * confidence + 0.25 * coverage`

### How To Choose A Heavy Provider
Use this rule:
1. prefer the provider with higher availability
2. if availability is similar, compare coverage
3. if both are similar, compare confidence
4. only then use readiness score as the final tiebreak

This is better than looking at confidence alone.

## Common Situations

### Situation A: Replay output is empty
Possible causes:
- report and labels do not reference the same image names
- the label file is for another batch

What to do:
1. verify image names in both files
2. regenerate the label template from the same report
3. rerun replay

### Situation B: Shadow classifier metrics are empty
Possible causes:
- the report was generated before shadow classifier fields existed

What to do:
1. rerun QA to generate a new `qa_report.json`
2. rerun replay benchmark on the new report

### Situation C: Heavy compare shows low availability
Possible causes:
- image root cannot be resolved
- heavy provider environment is unhealthy
- provider is not suitable for that sample set

What to do:
1. verify `--benchmark-image-root`
2. check provider status
3. inspect `missing_images`
4. inspect `failure_reasons`

### Situation D: Cache hit ratio is near zero on rerun
Possible causes:
- cache key changed
- source images changed
- provider version changed
- cache directory was cleared

What to do:
1. check `provider_version`
2. verify source files and timestamps
3. rerun once more on the same input

## Recommended Operating Sequence

### For Rule Regression
1. run QA once and save `qa_report.json`
2. create or update the benchmark label file
3. run replay benchmark
4. compare against the previous benchmark result

### For Heavy Provider Selection
1. run QA once and save `qa_report.json`
2. prepare a label file for the same batch
3. run `compare_heavy`
4. compare `segformer_body_fusion`, `segformer_parser`, and `body_measure_lite`
5. update the default provider only after benchmark evidence is clear

### For Shadow View Validation
1. generate a new QA report with current code
2. label lane and lane_detail
3. run replay benchmark
4. inspect:
   - `shadow_view_lane_accuracy`
   - `shadow_primary_lane_agreement`
5. inspect disagreement cases manually

## What Not To Do
- Do not run benchmark on a report and a label file from different batches.
- Do not use candidate-review labels as frozen benchmark truth.
- Do not judge a provider from one or two samples.
- Do not treat benchmark as final human arbitration.
- Do not interpret empty shadow metrics as a model failure before checking report freshness.

## Final Rule
- Benchmark exists to protect the review system from silent regression.
- Daily review decides the winner.
- Benchmark decides whether the evidence system is still trustworthy.
